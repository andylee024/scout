# Supabase Setup

This is the setup that works with Scout as it exists today.

## What Scout Uses Today

Scout currently expects:

- a `businesses` table
- a `contacts` table
- a `leads` view

Important current behavior:

- `scout run` upserts `businesses`
- `scout run` returns `listings` in the in-memory dataset, but does not persist them
- Clodo contacts go through `ingest-contacts` and `upload-contacts`
- `match-contacts` links `contacts.business_id` to `businesses.id`
- Google reviews are not wired in yet, but `businesses.place_id` is now required for that next step

## Environment Variables

Put these in `scout/.env`:

```bash
SUPABASE_URL="https://<project-ref>.supabase.co"
SUPABASE_KEY="<service-role-or-secret-key>"
```

Scout also needs:

```bash
GOOGLE_MAPS_API_KEY="..."
```

Use a key that can write to your project tables. The current pipeline uses the Supabase Python client and PostgREST.

## Recommended Setup Flow

1. Create a Supabase project.
2. Open the SQL Editor.
3. Run the schema below.
4. Add `SUPABASE_URL` and `SUPABASE_KEY` to `scout/.env`.
5. Run `scout verify businesses` to confirm the app can read the table.
6. Run one small import or `scout run` smoke test.

## Minimum Compatible Schema

Run this in the Supabase SQL Editor:

```sql
create table if not exists businesses (
  id bigint generated by default as identity primary key,
  source text not null,
  name text not null,
  place_id text,
  address text not null default '',
  city text default '',
  state text default '',
  phone text default '',
  website text default '',
  category text default '',
  rating double precision,
  reviews integer,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);

create unique index if not exists businesses_source_name_address_key
  on businesses (source, name, address);

create index if not exists idx_businesses_place_id
  on businesses (place_id);

create table if not exists contacts (
  id bigint generated by default as identity primary key,
  first_name text default '',
  last_name text default '',
  title text default '',
  company text not null,
  email text,
  linkedin text default '',
  website text default '',
  intent text default '',
  city text default '',
  state text default '',
  why text default '',
  signals text default '',
  source text not null default 'clodo',
  business_id bigint references businesses(id) on delete set null,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);

create or replace view leads as
  select
    b.id,
    b.source,
    b.name,
    b.place_id,
    b.address,
    b.city,
    b.state,
    b.phone,
    b.website,
    b.category,
    b.rating,
    b.reviews,
    c.first_name,
    c.last_name,
    c.title as contact_title,
    c.email,
    c.linkedin,
    c.intent,
    c.why,
    c.signals,
    b.created_at,
    b.updated_at
  from businesses b
  left join contacts c on c.business_id = b.id;
```

## Place ID Migration

If your `businesses` table already exists and only needs the Google place ID change, this smaller migration is enough:

## Why SQL Editor Instead Of Direct SQL API

For this project, the reliable path was the Supabase SQL Editor.

The direct `.../sql/v1` HTTP path returned `404 requested path is invalid` during setup, while:

- the SQL Editor worked for schema changes
- the REST API worked for verification after the schema was in place

So the practical rule is:

- use SQL Editor for schema changes
- use REST/CLI checks for smoke testing

## Smoke Checks

After setup, these are the fastest checks.

Verify the app can read the table:

```bash
cd /Users/andylee/Projects/scout
set -a && source scout/.env && set +a
scout verify businesses
```

Verify the `place_id` column exists through PostgREST:

```bash
cd /Users/andylee/Projects/scout
set -a && source scout/.env && set +a
curl -s -i "$SUPABASE_URL/rest/v1/businesses?select=place_id&limit=1" \
  -H "apikey: $SUPABASE_KEY" \
  -H "Authorization: Bearer $SUPABASE_KEY"
```

Expected result:

- `HTTP/2 200`
- response body can be `[]` if there are no rows yet

## Typical Workflow

### Option 1: Run the pipeline

```bash
scout run "fire protection in California"
```

Today this:

- fetches Google Maps and BizBuySell
- upserts `businesses` to Supabase
- returns `listings` in the run output only

### Option 2: CSV + contacts workflow

```bash
scout scrape-businesses "fire protection" "California"
scout upload-businesses outputs/businesses_fire_protection_California.csv

scout ingest-contacts data/clodo.csv
scout upload-contacts outputs/contacts.csv
scout match-contacts
scout pull-leads --output outputs/leads.csv
```

## Known Limits

- `listings` are not persisted by the current Supabase store
- raw payloads are not persisted by the current store
- contacts are inserted with client-side duplicate filtering, not a database uniqueness constraint
- lead merge is still partial; today the shared review surface is the `leads` view over `businesses` and `contacts`
